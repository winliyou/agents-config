# 复现鸿沟：用户持续复现而本机验证不出

> 2026-11-01 沉淀。来源于一次真实事故：同一个问题，用户在真实使用环境反复复现，验证方在另一套环境反复「验证通过」，于是多轮修改始终对不上。本文只保留可迁移的处置模式，不绑定具体项目、设备或分辨率。

## 0. 一句话

**当用户和你对同一个问题得出相反结论时，第一假设是「两个环境不同」，而不是「用户没看清」或「代码还没修对」。**

## 1. 这类问题为什么会反复错位

- 你验证出来的「正常」只是**你所在环境**的正常：你的屏幕尺寸与缩放、自动化工具默认视口、你的账号与数据、你的操作路径，通常都不等于用户的。
- 用户说「还是不行」是在描述**他的环境**；你不复现就改代码，等于在错误的输入上找错，改动越多，两边越对不上。
- 常见假设链及其实际概率：① 用户环境参数不同（显示/缩放/输入/数据/时序）→ ② 操作路径或触发状态不同 → ③ 用户描述的是另一个现象 → ④ 用户没更新/缓存没清。**④ 最常被当成第一假设，实际最少见**；顺序颠倒会让排查从一开始就跑偏。

## 2. 触发信号（满足任一，立刻切换流程）

- 同一问题用户反馈两次及以上，而你每次都验证通过；
- 你宣布修好后用户说「没变化 / 还是一样」；
- 现象与显示、设备、缩放、输入方式、账号或时序相关，只在特定条件下出现；
- 你开始怀疑「是用户操作有问题 / 环境脏」，但没验证过；
- 你已经改了几轮，每轮都「本机通过」。

## 3. 停止盲目修复（硬规则）

- **连续两轮「本机验证通过 + 用户仍反馈」后，禁止再直接改代码继续猜**。第二轮就必须转为「取证 + 参数化复现」，并在回复里明确告诉用户：现在进入环境取证，而不是再赌一次修复。
- 每轮修复的结论必须写清**验证环境参数**（窗口尺寸、缩放/像素密度、系统与客户端版本、账号与数据状态、操作路径），不能只写「已修复」。
- 用户确认前，措辞上限是「我在某环境验证通过，需要你在你的环境确认」；**不得宣布问题已解决**。

## 4. 先对齐「怎么算修好」

动手前用一句话和用户对齐验收口径：**在什么环境、做什么操作、看到什么结果**。口径没对齐时，你的「修好」和用户的「没好」可能根本不是同一个现象。

## 5. 环境取证（按成本递增，不要一次问一堆）

挑与现象最相关的两三个轴去问、去试：

| 轴 | 要问 / 要核对的点 |
|---|---|
| 显示与输入 | 屏幕分辨率、窗口大小、系统缩放与页面缩放、像素密度、多显示器、鼠标/触控板/触屏 |
| 平台 | 操作系统与版本、客户端或浏览器版本、字体与语言设置 |
| 身份与数据 | 登录账号与角色权限、本地缓存与持久化状态、时区与语言环境 |
| 时序与路径 | 精确操作路径、从哪个状态开始、是否每次必现、中间是否有等待或动画 |
| 依赖 | 连的是哪套服务端/哪个版本、是否有开关或灰度、网络状态 |

要**可核实的证据**，不要形容词：带指针位置的录屏、截图、复现概率、控制台或日志。信息不够时先要一段最小证据，而不是继续加代码猜。

## 6. 参数化复现：把「你的验证环境」当变量

- 把验证环境的可变参数显式列出来并尽量程序化改写（窗口/视口尺寸、缩放、DPI、输入坐标、数据状态、时序），至少跑两组：**用户给出的精确参数** + **边界值**。只跑默认值不算覆盖。
- **能算就先算**：动效、过渡、布局变化会让元素在触发瞬间位移，命中判定可以用坐标和元素矩形推算出「哪种尺寸下会失效」，再挑最可能的那档去实测，而不是穷举试错。
- **一次只改一个变量做二分**（缩放档位、窗口宽窄、输入设备、数据规模），现象从哪一档开始出现，分歧轴就锁定了。
- 自动化工具的默认环境尤其要警惕：无头或自动化模式的默认视口、缩放、字体往往与真实桌面不同，**别把工具默认值当成用户环境**。

## 7. 仪器化与远程取证

- 在关键路径打临时可观测标记（事件坐标、元素矩形、动画中间态、时序日志），让**用户在用户环境**跑一次最小诊断步骤，把「他的环境」变成你能读到的证据。
- 诊断入口要一键可开（开关、书签脚本、一条命令），不要要求用户陪你反复试；也不要把「让用户当测试员」当默认方案——先自己穷尽参数化复现。

## 8. 收敛与升级

- 取证后仍复现不出来：把信息整理成**分歧矩阵**（我的环境 / 用户环境 / 现象差异 / 已排除项）交给用户，并提出**具体**问题（给选项、给二选一的验证动作），而不是「你再试一次」。
- 确实无法本地复现时，如实交付「已确认的事实 + 下一步需要的信息」比假装修复更负责。

## 9. 反模式

- 用「我这边没问题，你再试试 / 清下缓存 / 是不是你环境的问题」结案；
- 反复在同一环境跑同一验证，并把它当成证据；
- 只验证默认分辨率、默认设备、默认账号；
- 修完不写验证环境参数，让用户一次次替你验证；
- 把用户反馈当噪音，或把用户当免费测试员；
- 一边说「修好了」，一边让用户重新描述同一个问题。

## 10. 修好之后（防复发）

- 把用户的真实环境参数加进回归矩阵（作为必须覆盖的一档），并让验证脚本支持参数化；
- 若这次暴露的是「验证环境不等于用户环境」的系统性盲区，把该盲区写进项目侧的 QA 或巡检清单；方法论留在本 skill。

## 11. 最小提问模板

> 我这边在「具体环境参数」下验证通过，但你的现象说明我们至少有一处不同。为了不让你反复试，我需要三条信息：
> ① 复现时的显示与设备参数（分辨率、缩放、窗口大小、设备型号）；
> ② 一段能看清操作和结果的录屏或截图（含指针位置更好）；
> ③ 是每次必现，还是特定条件下才出现？大概什么条件？
